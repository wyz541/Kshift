# ADR-0008 任务负责人和时区语义

> 结论：负责人是无序成员集合。项目时区决定自然日期。用户时区只决定绝对时间戳的显示。

> 历史说明：本 ADR 仅用于追溯。当前规则入口见 [Active Spec 索引](../specs/index.md)，目标 ID 为 `KS-DOMAIN`。

## 1. 状态

`accepted`

## 2. 背景

R1 合同已允许 `assignee_ids` 数组和项目 `time_zone`。此前 SwiftUI 按一个负责人处理任务。看板、筛选、拖拽和日期展示因此缺少一致语义。

团队可能跨时区工作。任务日期是计划日期，不是 UTC 时间点。客户端不能因用户时区改变任务日期。

## 3. 决策

### 3.1 负责人

- 一个任务有 0 至 20 个负责人。
- 负责人必须是当前项目的活跃成员。
- 负责人集合中的用户 ID 必须唯一。
- 空集合表示未分配。
- 写入替换完整集合。列表顺序没有业务含义。
- 服务端按用户 ID 升序输出负责人。
- 多负责人任务出现在每个负责人的人员列。
- 按人员筛选时，任务匹配任一所选负责人。
- 拖到人员列时，负责人集合替换为目标人员。
- 拖到未分配列时，负责人集合清空。

### 3.2 项目时区

- 每个项目有一个 IANA `time_zone`。
- 项目时区在创建项目时写入。首版不允许修改。
- 项目时区决定 `planned_on`、`starts_on` 和 `due_on` 的自然日期含义。
- 项目时区决定人员看板、日历、报告范围、今天和逾期判断。
- 自然日期保存为 `DATE`。服务端和客户端不得把自然日期当作 UTC 时间点。
- 修改项目时区属于后续决策。后续实现不得自动改写已有自然日期。

### 3.3 用户时区

- 用户时区来自当前设备，不是服务端业务字段。
- 用户时区只影响绝对时间戳的显示。
- 绝对时间戳在合同中保持 UTC RFC 3339。
- 用户时区缺失或非法时，客户端回退到项目时区。
- 用户时区不得改变任务的 `planned_on`、`starts_on` 或 `due_on`。

## 4. 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 单负责人 | UI 简单 | 不支持共同负责 | 拒绝 |
| 多负责人数组 | 表达完整；兼容合同 | 看板需要多列呈现 | 采用 |
| 按用户时区换算任务日期 | 本地午夜一致 | 任务日期漂移；共享视图冲突 | 拒绝 |
| 项目时区决定自然日期 | 团队看到同一计划日期 | 需要显示项目时区 | 采用 |
| 用户时区决定自然日期 | 符合个人本地时间 | 不同用户看到不同任务日期 | 拒绝 |
| 用户时区只显示时间戳 | 保留共享日期；保留本地时间 | UI 必须区分日期和时间戳 | 采用 |

## 5. 后果

- Swift 模型必须保留完整 `assignee_ids`，禁止只取第一项。
- 看板和筛选必须使用集合交集语义。
- 日期组件必须使用项目时区。
- 时间戳组件必须使用用户时区。
- Server 必须校验负责人所属项目。
- 删除项目成员时，必须在同一事务中处理相关任务负责人。具体成员删除命令属于 R4。

## 6. 验证

- Rust 测试覆盖负责人去重、20 人上限、空集合和非项目成员拒绝。
- Rust 测试覆盖 IANA 时区校验。
- Swift 测试覆盖多负责人映射、筛选和人员列重复显示。
- Swift 测试覆盖自然日期不随用户时区改变。
- 合同消费者只接收 opaque ID、自然日期字符串和 UTC 时间戳。
